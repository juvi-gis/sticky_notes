# Research Answers

## 1. Preserving state across HTTP requests

HTTP is a stateless protocol: each request is independent, and the server does not remember earlier ones. Applications add state on top, most commonly with sessions and cookies. When a user logs in, the server verifies their credentials, creates a session record holding data such as the user's ID, and sends the browser a random session identifier in a Set-Cookie header. The browser returns that cookie with every later request, so the server can look up the session and recognise the user. In Django, SessionMiddleware handles this: session data is stored server-side (by default in the django_session database table) and the browser only holds the sessionid cookie. Calling login() stores the user's ID in the session and rotates the session key to prevent session fixation, while logout() flushes it. Cookies should be marked HttpOnly, Secure and SameSite to reduce theft through scripts, network sniffing and cross-site requests, and CSRF tokens protect state-changing forms. Sessions can also expire after a set time. An alternative is token-based authentication, such as JSON Web Tokens, where the client sends a signed token with each request and the server keeps no session. Sessions are easier to revoke, while tokens scale more easily across servers.

## 2. Django migrations on MariaDB

To use MariaDB, install a database driver such as mysqlclient, create the database (with the utf8mb4 character set) and a dedicated user with privileges on it, then update the DATABASES setting to use the django.db.backends.mysql engine with the name, user, password, host and port. Credentials should come from environment variables rather than source control. Next, run python manage.py makemigrations to generate migration files from model changes; these files should be committed to version control and never edited once applied elsewhere. The sqlmigrate command shows the exact SQL a migration will run, which is useful for review. Running python manage.py migrate applies unapplied migrations in dependency order and records them in the django_migrations table, so each runs only once, and showmigrations lists the current status. On a production server, back up the database first, test the migrations against a staging copy, and run migrate as a deployment step. Because MariaDB does not support transactional DDL, a failed migration can leave the schema partly changed, so careful testing matters. Migrations can be rolled back by migrating to an earlier migration name.
